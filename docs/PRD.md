## 1. Vision and positioning

**One-liner:** A governed AI copilot that turns scattered access policies into a cited, approval-ready request in minutes instead of days, and never acts without a human saying yes.

**Why now:** Organisations are moving from AI pilots to AI that takes actions. The blockers are trust (can I verify the answer?), agency (will it do something I didn't approve?) and evidence (how do we know it's good?). This MVP is a reference pattern that addresses all three.

**How it differs from a typical RAG chatbot**

| Typical RAG chatbot | Enterprise Operations Copilot |
|---|---|
| Returns text chunks that look similar to the question | Traverses relationships: system → data class → controls → approvers → people |
| Answers without saying where facts came from | Every claim cited, gaps stated, confidence shown |
| Treats a meeting proposal and policy in force alike | Prefers effective-dated policy and flags proposals explicitly |
| Read-only, or acts unchecked | Drafts actions; executes only after explicit human approval enforced in code |
| "It seems good" | 30-case golden set, Baseline vs GraphRAG comparison, CI quality gate |
| A black box | Per-request traces, audit log, cost and latency per answer |

## 2. Problem

Before a contractor can access customer data, a sponsor has to work out which policies apply, what data the target system holds, which controls must be in place, which vendor checks are valid and who must approve, in what order. The answer spans 6–8 documents owned by different teams.

**Current state (scenario hypotheses, to validate in a pilot)**
- 2–5 business days to assemble a complete, correct request; most of it is waiting on email clarifications.
- Requests often reach Identity & Access missing an approver or prerequisite, so they bounce back.
- Gaps cause real incidents: INC-2026-031 (a contractor kept CRM access for 47 days after leaving) and INC-2026-044 (12,400 records exported without approval).

---

## 3. Goals and non-goals

**Goals (MVP)**
1. Answer direct and multi-hop access-governance questions with verifiable citations.
2. Prepare a complete, policy-compliant access request, with a human approval gate.
3. Prove quality with measured evals, including where GraphRAG helps and where it doesn't.
4. Demonstrate an operating model: observability, audit, governance, and a path to production.

**Non-goals (MVP)**
Real connectors (ServiceNow, SharePoint, Entra, HRIS); real provisioning; authentication and multi-tenancy; multiple workflows; production-scale graph database; mobile UI.

## 5. End-to-end user journey (hero flow and demo script)

**Scenario:** Tom Gallagher (Customer Platforms) is the sponsor for contractor Alex Chen, who needs to analyse customer churn in Atlas CRM. There's no authentication in the MVP, so the user states who they are in the prompt.

**Two kinds of approval. Don't confuse them in the demo:**
- **Action confirmation (human-in-the-loop):** the user explicitly confirms that the copilot may perform a write action, here submitting the request. Enforced in code (FR-010).
- **Organisational approvals:** the line manager, data owner, Security Governance and Privacy Officer sign-offs from REF-005. These happen in the (simulated) ITSM workflow after submission. The copilot never records them on anyone's behalf.

### 6.3 Other views
- **Audit log:** timestamp, actor (as stated by the user, unverified in the MVP), event (`proposed` · `blocked` · `confirmed` · `cancelled` · `executed`), draft ID, request ID, policy citations. Read-only.
- **Eval dashboard:** latest run, metric × mode table, per-category bars, link to the CI run.

**UX principles:** show the source before the claim; one primary action per card; uncertainty is shown (confidence, gaps), never hidden; anything simulated is labelled.

## 8. Non-functional requirements

### 8.1 Security: OWASP Top 10 for LLM Applications (2025) mapping
| Risk | Mitigation in MVP | Verified by |
|---|---|---|
| LLM01 Prompt injection (direct; and indirect, via retrieved documents) | Retrieved text treated as data, never as instructions; tool allow-list; write tools gated in code, so an injection can't trigger an action | GS-027 (direct); add an indirect-injection document in the pilot |
| LLM02 Sensitive information disclosure | Copilot holds governance knowledge only, no customer records; PII redaction in traces | GS-028, FR-017 |
| LLM03 Supply chain | Pinned dependency versions; lockfile committed; Dependabot alerts | CI |
| LLM04 Data and model poisoning | Corpus is fixed and committed; any change goes through PR and `validate_seed.py` | CI |
| LLM05 Improper output handling | Tool arguments validated against schema (Zod) before any call; model output rendered as sanitised Markdown, never raw HTML | Unit tests |
| LLM06 Excessive agency | Only 2 write tools, both mock, both confirmation-gated; read / propose / write risk declared per tool (the agent gets read + propose only); social-engineering pressure ("skip approvals") refused | SC-006 = 100%; GS-026 |
| LLM07 System prompt leakage | No secrets in prompts; keys only in env vars | Code review |
| LLM08 Vector and embedding weaknesses | Ingestion only from the committed corpus; doc_id provenance on every chunk | validate_seed.py |
| LLM09 Misinformation | Grounded-or-silent rule; citation accuracy gated in CI | SC-001, SC-002, GS-017, GS-019 |
| LLM10 Unbounded consumption | Max tokens per request, max tool-call iterations (≤ 6), rate limit on the public demo | Config and tests |

### 10.3 Production path (AWS first; Azure equivalent)

The MVP is cloud-neutral by design. The primary production target is **AWS with Amazon Bedrock**. The Azure column shows the same design on Microsoft 365.

| Concern | MVP (this weekend) | **AWS production (primary)** | Azure / M365 equivalent |
|---|---|---|---|
| Model | Anthropic API, or Bedrock via `MODEL_PROVIDER` | **Claude on Amazon Bedrock** (Converse / InvokeModel), in-region (e.g. ap-southeast-2) | Claude via Microsoft Foundry |
| Safety filters | Code-level checks and golden-set safety cases | **Amazon Bedrock Guardrails**: PII masking, prompt-attack filter, denied topics, applied to inputs and outputs | Azure AI Content Safety, Prompt Shields |
| Document retrieval | Neon pgvector + full-text search | **Amazon Bedrock Knowledge Bases** over S3, with an OpenSearch Serverless or Aurora PostgreSQL (pgvector) vector store; hybrid search | Azure AI Search (hybrid + semantic ranker) |
| Policy graph | Postgres `nodes` / `edges` with recursive CTEs | **Amazon Neptune Analytics** with our own schema, queried with openCypher (see note) | Cosmos DB for Apache Gremlin, or Neo4j |
| Source content | Markdown in the repo | S3, synced from Confluence / SharePoint connectors | SharePoint / Confluence via Microsoft Graph connectors |
| Agent runtime | Tool-use loop in a Next.js route | Same loop on **AWS Lambda** or **ECS Fargate**; optionally **Amazon Bedrock AgentCore** for managed agent hosting | Azure Container Apps / Functions |
| Tools | In-process MCP server, mock tools | MCP servers wrapping ServiceNow / Jira APIs, behind API Gateway, with IAM-scoped credentials per tool | MCP servers behind API Management; Power Automate |
| Approval orchestration | Durable **Vercel Workflow**: hook per approver, SLA `sleep()` race (fallback: in-memory state machine) | **Amazon EventBridge** (`access_request.submitted`) → **AWS Step Functions** standard workflow: one task-token callback step per approver, SLA timers with escalation, audit on each transition | Power Automate approvals / Logic Apps; Event Grid |
| Identity and access | None (user states identity) | IAM Identity Center / SAML SSO; document-level permission filtering via Knowledge Base metadata filters | Entra ID SSO; security trimming; Purview labels |
| Observability | Langfuse; `audit_log` table | Langfuse or OpenTelemetry → **CloudWatch** / X-Ray; Bedrock model invocation logging; audit events archived to S3 (Object Lock) | Application Insights + OpenTelemetry |
| CI/CD | GitHub Actions with eval gate | GitHub Actions or CodePipeline: eval gate → CDK / Terraform deploy | GitHub Actions / Azure DevOps |

**Why a hand-modelled graph, not managed GraphRAG, for policy logic.** Bedrock Knowledge Bases has a managed GraphRAG option on Neptune Analytics, but it builds the graph automatically from documents and doesn't support customising how the graph is built. Approval logic depends on exact, conditional edges (`requester=Contractor`, `classification=Restricted`), so we keep our own curated schema in Neptune Analytics for policy reasoning. Managed Knowledge Bases (vector, or managed GraphRAG) can still handle unstructured documents. The evals decide which approach wins for each question type.

## 11. Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Hallucinated policy detail | Medium | High | Grounded-or-silent rule; citation checks gated in CI; confidence and gaps shown |
| Prompt injection triggers an action | Medium | High | Approval enforced in code; tool allow-list; injection cases in golden set |
| Users over-trust the copilot | Medium | High | Citations first; "decision support, not decision maker" copy; humans approve |
| New SDK (Vercel Workflows) slows the weekend | Medium | Medium | Time-boxed to M4 with a same-interface in-memory fallback (ADR-006) |
| Action confirmation mistaken for organisational approval | Medium | High | Distinct wording ("Submit request", not "Approve"); request status shows pending approvers; audit events separate `confirmed` from approvals |
| Unverified identity in the MVP (no auth) | High | Medium | Actor recorded as "stated, unverified"; Entra ID SSO is a production prerequisite (§10.3) |
| Stale or conflicting sources | Medium | Medium | Effective-date metadata; proposal vs policy rule (FR-008); owner shown per doc |
| GraphRAG adds cost without benefit | Medium | Medium | Router sends simple lookups to cheaper text-only path; publish where baseline wins |
| LLM-as-judge bias | Medium | Medium | Different judge model; manual spot-check of ≥ 10 cases; report judge used |
| Weekend scope overrun | High | Medium | Milestones, cut line, Sunday 12:00 freeze |
| Public demo abuse or cost spike | Low | Medium | Rate limit; daily spend cap; synthetic data only |
| Model or provider lock-in | Low | Low | Model behind an interface; evals make swapping measurable |

1. Approval orchestration now uses a durable Vercel Workflow: a hook per approver, an SLA `sleep()` race and an audit step per transition. The in-memory state machine is kept as a time-boxed fallback (FR-024, ADR-006).
2. Approver hooks are resumable only from a labelled *Simulated approver* panel, never by agent tools (FR-024a). SLA time scaling and auto-delete for demos (FR-024b).
3. Estimated added cost: about $0.001 per request (about 40 workflow events); suspended runs use no compute.

**v1.2 (2026-11-13): JD alignment (AWS, orchestration, leadership)**
1. §10.3 rewritten AWS-first (Bedrock, Guardrails, Knowledge Bases, Neptune Analytics, EventBridge + Step Functions, AgentCore option), with an Azure column. Explains why policy logic uses a curated graph instead of managed GraphRAG.
2. Hero step 6 now emits a domain event and shows the simulated approval state machine (FR-024).
3. Added a model provider switch, Anthropic or Bedrock (FR-025). Agent runtime changed from the Claude Agent SDK to a tool-use loop on the Anthropic SDK, which deploys safely on Vercel (CLAUDE.md ADR-003).
4. Spec: explicit intent → route table (FR-005a) and graph seed modes for corpus-wide questions (FR-005b); MCP runs in-process (FR-014).
5. Added `PLAYBOOK.md` and leadership evidence in the launch plan.

**v1.1 (2026-11-13): review corrections**
1. Split "approval" into **action confirmation** (the user lets the copilot submit) and **organisational approvals** (REF-005 sign-offs in the ITSM workflow). v1.0 implied that clicking Approve granted the request.
2. Renamed retrieval modes to `baseline` (hybrid keyword + vector, no graph) and `graphrag`, and the route to `text`. "Vector-only" contradicted FR-004, which already makes the baseline hybrid. Updated in the spec, golden set, evaluation README, validator and CLAUDE.md.
3. Removed the pre-scripted baseline result from demo step 3. The demo shows measured output only (Constitution VIII).
4. Demo step 4: the user now states who they are (no auth in the MVP), the copilot asks for the missing justification, and the exception limit (30 days, POL-014 §4) is stated correctly.
5. Wireframe controls now include masking (CTL-05) and bulk export approval (CTL-08), which apply to Customer PII. "NDA" renamed to the policy term, confidentiality agreement.
6. Added a separation-of-duties warning: in the hero scenario Tom Gallagher is both sponsor and data owner.
7. Vendor check shown as an assumption ("not stated"), not a ✔.
8. One-liner aligned with the §9.1 target ("minutes instead of days", not "under a minute").
9. OWASP mapping: added LLM03 and LLM04 and indirect prompt injection; GS-026 moved to LLM06 (it's social engineering, not injection); LLM05 now covers output rendering.
10. Demo step 8 and step 3 now have fallbacks for features that may be cut.
11. Added two risks: confirmation mistaken for approval, and unverified identity.
12. RACI: pilot go/no-go is accountable to a business sponsor, not Security Governance.
13. Status, M0 and §9.2 wording no longer claim work that hasn't happened yet (committing, measuring).
